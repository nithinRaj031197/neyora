# Orders

A customer picks a variety and a quantity, gives a delivery address, and pays
the rider. Nothing is charged online. The order is stored in MongoDB, the admin
is emailed, and the order is projected into a Google Sheet for reporting.

```
Customer
   ↓
Place order
   ↓
MongoDB  ← the source of truth, always
   ↓
success returned to the customer
   ↓
background, never blocking:
   ├── admin email
   └── Google Sheets row
```

Nothing after the MongoDB write can fail the order. That is the single rule
this whole design exists to keep.

## Setup

Only `MONGODB_URI` is required. Every other integration is optional: without
credentials the channel records `skipped`, and the site works completely.

```
MONGODB_URI="mongodb+srv://USER:PASSWORD@cluster.xxxxx.mongodb.net/?retryWrites=true&w=majority"
MONGODB_DB="neyora"
```

Atlas: free M0 tier, AWS, **Mumbai (ap-south-1)** — the customers are in India
and a database in Virginia adds a quarter-second to every order.

**Network Access must stay `0.0.0.0/0`.** Cloudflare Workers egress through
undocumented, non-static WARP ranges; static egress IPs are Enterprise-only.
Restricting by IP would break production. The password is therefore the entire
security boundary: use an autogenerated one, scope the user to `readWrite` on
the `neyora` database only, and keep a separate user for local development.

See `.env.example` for the email and Google Sheets variables.

## Shape

The collection has no schema of its own — MongoDB stores whatever it is given —
so `lib/orders/schema.ts` is the only thing preventing a bad row. Every write
goes through it.

| Field | Notes |
| --- | --- |
| `reference` | `NEY-0001`. Unique, monotonic, issued by an atomic counter. |
| `status` | `new → confirmed → preparing → out_for_delivery → delivered`, or `cancelled` from any live state |
| `customer` | name, phone, full `address`, optional note |
| `customer.address` | `line1`, `line2?`, `area`, `city`, `pincode`, `landmark?` |
| `items[]` | slug, name, variety, pack label, weight, unit price, quantity |
| `total` | **Computed server-side.** Never posted by the form. |
| `payment` | `{ method, status, paidAt?, updatedBy?, history[] }` |
| `notifications` | per channel: status, attempts, sentAt, lastError |
| `sheetSync` | how far behind the spreadsheet is |
| `idempotencyKey` | per form mount; unique-indexed. Stops a double-tap |
| `history[]` | every status change, with timestamp and admin |

Phone numbers are stored as ten digits. `+91 98765 43210`, `098765-43210` and
`(+91) 9876543210` all become `9876543210`, so a returning customer is one
customer.

## Rules worth knowing

**Price comes from the server.** The form posts a slug and a quantity, never a
price. `placeOrder` looks the product up and recomputes the total.

**Availability is enforced server-side.** A stale tab or a crafted POST cannot
order a sold-out variety — the action re-checks, it does not rely on the form
being hidden.

**Delivery is Bengaluru only.** `lib/orders/delivery.ts` holds the rule, and
documents that `56xxxx` is a broad regional check rather than a serviceability
guarantee. Moving to an explicit pincode list is one constant in that file.

**Payment is separate from status.** A delivered order is not automatically a
paid one — the rider can hand over the pack and come back without the cash.
Marking paid is always explicit, and reversals are kept in `payment.history`
rather than erasing the fact that payment was once recorded.

**Status transitions are checked in the query.** `advanceOrder` matches on the
current status, so two admins acting at once cannot both succeed.

## Pagination

The admin list is cursor-paginated on `(createdAt, reference)`, 20 at a time.
Not skip/offset: `skip` re-walks every preceding document, and an order placed
mid-paging shifts every later page — silently duplicating one order and hiding
another. `reference` is the tiebreak because `createdAt` alone is not unique.

## Indexes

Created on first write by `ensureIndexes`, which is idempotent.

| Index | Serves |
| --- | --- |
| `{ reference: 1 }` unique | lookup, and the cursor tiebreak |
| `{ createdAt: -1, reference: -1 }` | the default list and the cursor |
| `{ status: 1, createdAt: -1, reference: -1 }` | status filter |
| `{ 'payment.status': 1, createdAt: -1, reference: -1 }` | payment filter, unpaid total |
| `{ 'customer.phone': 1, createdAt: -1 }` | customer history, search |
| `{ idempotencyKey: 1 }` unique sparse | duplicate submission |
| `{ 'sheetSync.status': 1, createdAt: -1 }` sparse | the sync sweep |

## Google Sheets

**One way, MongoDB → Sheets. Never the reverse.** If the sheet disagrees with
the database, the sheet is behind and gets rewritten; nothing read from it ever
reaches an order.

One row per **order item**, keyed `NEY-0021#1`. That key makes the write an
upsert: a retry updates the row rather than appending another. Reporting works
because every variety is its own row — `SUM(Line Total)` is revenue,
`COUNTUNIQUE(Order Reference)` is the order count.

**It never deletes a row.** A sheet row with no matching order — history, an
archived order, a line typed by hand — is counted and left alone. Duplicate Row
Keys are reported for review, never removed automatically.

**Sync All** (admin dashboard) reconciles 25 orders per press, resumable by
cursor, guarded by a MongoDB lock so two admins cannot both append the same row.

Customer-typed values are escaped against spreadsheet formula injection: a name
of `=IMPORTXML(...)` is stored as text, not run as a formula.

## Retries

`ctx.waitUntil`, not `after()` — the latter is an open bug on OpenNext
Cloudflare (#912) and is intermittently cut off in production.

If a channel fails it is recorded on the order, badged in the dashboard, and
retryable by hand. `POST /api/sync/retry` sweeps both email and Sheets; it
returns 404 unless `SYNC_RETRY_SECRET` is set, so it does not exist until
configured. Point any scheduler at it.

## Deployment

Secrets go in with `npx wrangler secret put NAME` — never in `wrangler.jsonc`,
which is committed.
